# Безопасность персонального KIT

KIT защищает соединение устройства с вашим VPS и предоставляет несколько транспортов. VPS, его хостер и устройство остаются доверенными участниками. KIT не защищает от вредоносного ПО на телефоне, компрометации root на VPS, фишинга или наблюдения конечного сайта. Общий IP и общий nginx — общие точки отказа; смена транспорта не устраняет блокировку самого IP.

## Subscription URL — секрет

Каждое устройство получает случайный 128-битный токен, общий префикс URL также случайный (128 бит). QR содержит тот же секрет. У кого есть URL, тот может получить ключи устройства. Не храните URL в git, публичных чатах, issue, скриншотах и сторонних конвертерах подписки. User-Agent выбирает формат, но не является проверкой личности; доступ защищён токеном.

При утечке: `kit user off имя`, затем создайте пользователя с новым именем и замените URL на соответствующем устройстве. Остальные устройства не меняйте. При потерянном телефоне отключите его пользователя. `kit user del имя` окончательно удаляет основную и связанные AWG-записи. Проверьте, что прежние подключения перестали работать, включая AWG.

## Панель и root

Панель и нативный backend подписки слушают 127.0.0.1. В nginx нет маршрута к панели. Открывайте её только через SSH-туннель с фактическим портом из installer output. Root нужен installer и обслуживанию, но не для постоянной работы графического VPN-клиента на ПК. Секреты панели и API-token хранятся в root-файлах с правами 0600. Не включайте shell tracing (`set -x`) при работе с KIT.

Логи KIT не содержат пути подписок, ключей или произвольного User-Agent. Лог стороннего установщика `/var/log/3x-ui-install.log` может содержать credentials, поэтому права 0600. При диагностике сторонних служб сами просматривайте журнал перед передачей: запрет логирования KIT не делает произвольные журналы 3X-UI/Xray безопасными для публикации.

## SSH: безопасный порядок

`kit harden ssh` показывает рекомендации и ничего не меняет. Автоматически отключать пароль или root-login опасно: наличие файла authorized_keys не доказывает рабочий вход.

1. Убедитесь, что доступна консоль восстановления хостера. Оставьте текущую SSH-сессию открытой.
2. При желании создайте отдельного пользователя: `adduser vpnadmin`, затем `usermod -aG sudo vpnadmin`.
3. На своём ПК установите **public key**: `ssh-copy-id vpnadmin@SERVER_IP` (для другого SSH-порта добавьте `-p`). Private key на VPS не копируйте.
4. В НОВОМ окне войдите по ключу: `ssh -o PreferredAuthentications=publickey -o PasswordAuthentication=no vpnadmin@SERVER_IP`. Проверьте `sudo -v` и `sudo -i`.
5. Только после этого рассматривайте `PasswordAuthentication no`, `KbdInteractiveAuthentication no` и запрет root-login в конфигурации sshd. Сохраните прежнюю конфигурацию. Проверьте `sshd -t` и эффективные настройки `sshd -T`: cloud-init и другие include могут переопределять их.
6. Reload выполняйте только после успешной проверки, не закрывая старую сессию. Откройте ещё одно новое подключение и проверьте sudo.
7. При ошибке восстановите прежние файлы из старой сессии или консоли VPS и снова выполните `sshd -t`.

При утечке SSH private key: удалите соответствующий public key из authorized_keys всех затронутых серверов, создайте новую пару на доверенном ПК, проверьте новый вход. Проверьте другие ключи, пользователей и журналы входа. Если злоумышленник мог получить root, считайте VPS скомпрометированным.

## Firewall

UFW получает только порты выбранных протоколов и реальные SSH-порты. Если определить SSH-порт не удалось, installer не включает UFW автоматически. Существующие правила не сбрасываются; проверьте их сами. Не используйте `ufw reset` удалённо. Firewall хостера настраивается отдельно. Сертификату IP нужен постоянно доступный 80/tcp для HTTP-01; внутренние localhost-порты в firewall не открываются.

## Backup и восстановление

`kit backup` сохраняет согласованную SQLite DB, настройки KIT/3X-UI/nginx/systemd, сертификаты, ACME-account и CLI. Права архива 0600, каталога 0700. Он содержит credentials всех устройств и ключи сервера. Скопируйте его за пределы VPS по SSH и храните зашифрованным в доверенном хранилище. Архив не зашифрован самой командой KIT.

Не восстанавливайте чужие/непроверенные архивы и не запускайте `tar -x` сразу в `/`. Порядок ручного восстановления с проверкой и предварительным backup — [INSTALL.md](manuals/INSTALL.md). PostgreSQL и кастомные пути DB этим backup не поддерживаются. Symlink-файлы пропускаются; стандартная установка использует обычные файлы, нестандартные ссылки нужно сохранить отдельно.

## GitHub и upstream

Runtime repository: McElast/3x-easy-one. Production — конкретный stable tag или commit SHA; main используется только для разработки. Installer получает все файлы KIT из одного архива. Не передвигайте опубликованные теги. HTTPS и checksum подтверждают целостность скачивания, но не исключают компрометацию GitHub-аккаунта; используйте 2FA и review diff.

3X-UI v3.8.5 и Xray v26.6.27 сохранены из исходного KIT. Официальный installer 3X-UI проверяет checksum релиза, если опубликован. API этой версии панели проверяет SHA-256 Xray по официальному `.dgst`. acme.sh 3.1.6 проверяется фиксированной SHA-256; его auto-upgrade не включён. Standalone Hysteria 2.12.3 проверяет официальный hashes.txt. Проверка обновлений KIT читает метаданные, не исполняет скачанный код.

Исходный [itsnotkubrick/3X-UI_KIT](https://github.com/itsnotkubrick/3X-UI_KIT) изучается вручную: diff → review → перенос нужных изменений → наш release. Автоматическое исполнение upstream/main запрещено. Внешнее меню x-ui не переписывается cron-задачей.

## Если VPS скомпрометирован

Отключите его в панели хостера, сохраните необходимые сведения для расследования, разверните чистую ОС на доверенном VPS. Смените доступ к хостеру, SSH-ключи, пароли панели, API-token, сертификатные ключи и ВСЕ ключи устройств/подписки. Не восстанавливайте исполняемые файлы и неизвестные конфиги из подозрительного backup без проверки. Проверьте устройства, с которых администрировали сервер. Компрометация root затрагивает все устройства, а не один пользовательский URL.

## Клиенты и полный VPN

Включайте TUN/режим VPN, а не только System Proxy, если нужен весь интернет устройства. Используйте Rule с единственным финальным направлением VPN и локальными исключениями. Включите в клиенте блокировку/туннелирование IPv6, если он не поддерживается вашим профилем; IPv4-сервер сам по себе не запрещает приложениям прямой IPv6. До и после подключения проверьте внешний IPv4/IPv6 и DNS. KIT не включает kill switch автоматически: проверяйте настройку клиента и возможность восстановления сети.

DNS/health-check делают функциональные запросы к выбранным URL. KIT не добавляет аналитику/remote logging. Сетевые запросы GUI (обновления, IP-карточки, диагностика) и политики приватности приложений независимы от KIT.
